# ZeroEngine 可信排行榜平台 Spec

- 状态：Draft，供确认实施范围；本文不代表下列能力已经实现或上线。
- 日期：2026-11-12。
- 本轮实施范围：仅备份完整性、历史清理和忙锁容错；手机、自有排名存储与客户端 SDK 提取仍保留为后续方案。90 天墓碑清除也不在本轮，保留现有只裁剪中间回执的行为。
- ZE 核对基线：`5036b0720c9d88bfb7d8d30af57290026e2c3f06`；现有公共内核见 [Services/leaderboards](../../Services/leaderboards/README.md)。
- POB 服务端采用基线：Plastic `cs:19092`，固定 ZE 源快照 `a1c4d3541ceb5ff943ccbb4076e96814bf82c742`；上海部署核验截至 2026-11-12。本 spec 不改变该部署。

## 1. 推荐方案与验收边界

采用一个 ZE 排行榜 SDK、一套服务端内核和项目适配器。Steam 作为可选平台接入；未来手机端由自有服务存储成绩、计算排名并提供查询，不依赖 Steam 的排行榜存储。

先修现有 POB 的备份、历史清理、忙锁处理和选榜一致性，再提取客户端 SDK。自有排名存储与首个手机渠道在后续独立阶段接入，不作为当前 POB 修复的前置条件。

“尽量免维护”定义为：普通发版、关卡配置调整、周常轮换、同规则赛季创建，以及日常历史清理、备份轮转和进程重启，不要求逐次手改服务端。破坏性规则变更、平台认证政策变化、密钥轮换、扩容和灾难恢复仍有明确操作入口。

POB 达到本文 P0–P2 的验收条件，可以独立交付；只有 P3 的真实平台认证、自有读写榜及恢复演练也满足条件，才能称为手机端可用。接口可替换或模拟测试成功不等于手机服务已上线。

## 2. 已有能力与需要补齐的部分

| 范围 | 核对结果 | 本方案处理 |
| --- | --- | --- |
| 通用 Python 内核 | 已有身份验证接入、对局凭据、序号/nonce、幂等回执、事件合批、发布状态和历史裁剪 | 复用现有实现，修补清理与存储异常处理 |
| POB 适配 | 已保留玩法规则、榜名、周期种子、房间语义与客户端存档集成 | 继续由 POB 拥有，统一榜名解析入口 |
| 部署恢复包 | 当前备份脚本只收应用根目录的 Python 文件，会漏掉新公共模块目录和来源清单 | 优先修复并做隔离恢复，不能只看备份任务退出码 |
| 历史清理 | 当前请求路径内持 SQLite 写锁筛选历史，存在全表及相关子查询扫描 | 改为有索引、分批、可续跑的独立维护入口 |
| SQLite 忙锁 | 未统一映射为可重试的服务暂不可用 | 只识别 busy/locked，避免把其他数据库错误吞成网络问题 |
| RP1 榜名 | 新赛季自动模板、预取/导出和实际提交存在不一致边界 | 服务端按规则族选模板，客户端共用解析器 |
| ZE Unity SDK | 尚未独立成 UPM 包 | 从已验证的 POB 实现提取，不重写一套并行流程 |
| 手机排行榜 | 尚无真实渠道认证、自有排名表及完整查询 API | P3 补齐；模拟非 Steam 身份仅证明扩展边界 |

容量风险需要长期预算和压力验证，不能由几天的库大小推断必然失控。SQLite 删除后可复用空闲页；文件未缩小本身不代表清理无效。上述问题也不等于当前所有玩家正在写榜失败。

## 3. 模块归属

| 模块 | 负责 | 保持在项目/平台适配器中的内容 |
| --- | --- | --- |
| `com.zerogamestudio.zeroengine.leaderboards`（拟新增） | Unity 协议、异步传输、持久发送队列、恢复重试、查询缓存和状态事件 | 游戏存档、结算入口、具体 UI、本地化文本、Steam/手机渠道 SDK |
| `Services/leaderboards/ze_leaderboards` | 服务端凭据、幂等、生命周期、存储事务、排名存储/查询、维护与恢复公共逻辑 | POB 房间校验、分数算法、榜名与周常规则 |
| 项目服务入口 | 项目配置、玩法验证、模式/赛季映射、部署绑定 | 不复制公共收据和发送状态机 |
| 平台适配器 | 验证渠道凭证；可选外部榜发布/查询 | 不信任客户端自报的平台身份或最终分数 |

Unity 包运行时命名空间采用 `ZeroEngine.Leaderboards`，不引用 POB 类型、Steam SDK 或具体 UI。需要的 Editor 导出工具放独立 Editor 程序集；新增资产保留 `.meta`，包具有 `package.json`、程序集定义、README、CHANGELOG 和聚焦测试。

服务端继续作为 Python 库，不能装入客户端 UPM 包或携带发行商密钥。各游戏独立服务实例、数据库、签名密钥和平台配置；可以共用机器及代码版本，不复用 POB 的可写账本。首版不建设多租户路由、中央账号平台、Redis 或集群调度。

消费项目通过 Git UPM URL 固定已验证的 ZE commit；同项目 ZE 包保持同一 commit。服务端消费固定源码快照及 `zeroengine-source.json`，部署时不临时拉取浮动分支。Unity SDK 与 Python 内核各自声明协议兼容范围，不要求每次 SDK 小版本都同步部署服务。

## 4. 认证、可信校验与正常玩家保护

认证器将经过服务端验证的平台凭证转换为稳定的项目内 `subject`，平台命名空间参与身份隔离。Steam 使用 Steam 认证；手机选择首发渠道后实现一个真实认证适配器。设备 ID、昵称和客户端传来的账号字符串不构成认证。跨渠道账号绑定必须证明两边账号归属，首版不按昵称自动合并。

客户端开局异步领取对局凭据，进度合批，结算异步补传；局内玩法不等待 HTTP。凭据、发送序号、结算快照及发送队列持久化，正常退出、读档、移动端切后台或重启后继续原局。POB 保留已经约定的旧局迁移规则，不在公共包内重新解释游戏存档。

发送队列按事件数、字节数和有效期设预算，已确认请求及时回收，可选观测在入队前限量；已入队请求不随意改写，未确认的终局不能静默丢弃。达到容量或落盘失败时保留可恢复状态并报告同步问题，不转换成玩法校验失败，也不每帧刷盘或无期限堆积。

POB 在死亡/最终结束事件封存结果，后续进入结算 UI、重复回调和读档不重算成绩。训练木桩等非计时房由项目的房间语义声明排除，不由通用层识别房名。SDK 提供可靠持久化入口，项目负责在终局和存档切换前调用；本地落盘成本也需要测量，不能把“异步联网”当成完全没有主线程开销。

客户端仅在开局收到 `invalid_ticket` 时，允许换新凭证重试一次，沿用同一对局 ID 与初始时间；取消或放弃后不继续登记。限制必须跨回调生效，服务端继续验证新凭证并按逻辑对局去重。已经存在的修复先核对客户端实际包版本，不重复实现。错误日志记录来源、数字错误码及阶段，不能把所有凭证错误都解释为过期。

超时、限流、连接中断和存储忙锁属于可重试结果，不撤销正常对局。明确的玩法矛盾、过期凭据和身份拒绝保持各自结果；玩家提示区分“待同步”“本局未完成登记”“旧规则对局不计入”及“本局未通过校验”。网络失败不能提示玩家作弊。

服务端不可用时不放开客户端直写可信榜。已经登记的局在凭据有效期及可恢复账本范围内补传；开局始终拿不到凭据的局仍可正常游玩，但不承诺事后补成可信局。单机本地战斗不具备服务器战斗模拟的保证，合法路线中的改血/改攻击不能仅凭房间打卡完全排除。

房间校验依赖玩法语义和构建导出的配置，不维护一串特殊房间名补丁。辅助属性快照缺失或出现未知可选观测，只记录可诊断信息；只有明确违反该规则族的必要条件才拒绝。允许的主线、旁路、回访、续玩和终局路径，由项目配置生成相应合同测试。

## 5. 自动版本兼容与选榜

引入项目内唯一的榜标识解析入口，返回逻辑榜、规则族、目标榜和环境。提交、预取、展示、构建导出与测试使用同一个结果；POB 按实际 RoomPlan 是否配置决定 RP1 或旧规则，不能无条件追加后缀。

正常的显示版本号升级不作为拒绝条件。协议、规则族和计分语义兼容时自动接纳；新房间或路线配置由可信构建链路自动导出、校验并同步。服务端不因客户端自报的版本/哈希而相信新的游戏规则，也不把 Steam 身份验证当成分支或二进制完整性证明。

自动创建榜只使用服务端批准的模式模板、规则族、赛季和日期范围，并有创建数量预算；未知字符串不能随意创榜。RP1 与旧规则分别选模板，模板缺失时不得跨规则族静默套用。

发布分支映射沿用项目约定：正式包写正式环境，其他包写测试环境。环境隔离由服务端配置约束目标榜与可用凭证；客户端分支名主要承担路由，不作为安全凭证。

已登记对局冻结其规则快照，兼容更新不改变在途局判定。改变计分单位、必要验证语义或公平性的更新，应明确提升协议/规则修订或开新榜；由构建门禁识别并要求一次决策，不自动把不同规则混在一榜。旧赛季继续可查，不自动迁入未经验证的历史分数。

构建链路负责导出和比较，服务端负责批准模板与原子应用；普通更新无需手改 `policy.json`。策略合并保留兼容组合的配对关系，禁止 `rules × content` 隐式交叉；过期组合在所有在途局及回滚窗口结束后自动归档。

## 6. 手机端自有排行榜

### 6.1 一个榜只有一个权威目标

| 方式 | 权威数据 | 行为 |
| --- | --- | --- |
| `SteamPrimary` | Steam 成绩 | 当前 POB 保持现状，读榜仍走 Steam；本轮不迁移历史成绩 |
| `InternalPrimary` | 自有数据库成绩 | 手机或新项目通过自有 API 读写；Steam 可作为独立、可选镜像 |

镜像失败只影响镜像状态，不能将已经成功的自有成绩改为失败，也不能反过来冒充镜像成功。写 Steam 镜像需要玩家已经验证并绑定 Steam 身份。跨平台同榜须由项目明确允许的平台及一致的计分规则，不默认把所有平台混排。

### 6.2 最小数据与事务

自有存储先使用同实例 SQLite，复用连接和运维方式，只有实际容量、读写并发或可用性要求超出预算时再采用现有 PostgreSQL 适配。排名数据与对局审计逻辑分离，但同一权威写入使用同一个数据库事务。

- `boards`：逻辑榜 ID、规则修订、方向、分数单位、目标类型及可查询状态。
- `leaderboard_entries`：`board + subject` 唯一，保存最佳分数、取得时间、来源对局和更新版本。
- 现有对局/回执表：验证过程、幂等与结算结果；到期清理不删除已经入榜的最佳成绩。

分数采用明确定义的整数单位，由项目验证器计算。最佳成绩原子更新；同分保留原取得时间。默认按分数方向、取得时间、稳定 subject 排成唯一顺序，名次使用同一排序；若项目需要并列名次，作为榜级显式规则，读写及翻页一致。

自有榜发布必须在一次事务内写入最佳成绩、对局发布结果和回执。提交后响应丢失时，通过原对局 ID 查询/重放确定结果，不能重复累计，也不能沿用外部 Steam 发布的“不知道是否写入”处理来永久卡住本地成绩。Steam 的外部写入状态机保持独立语义。

### 6.3 查询与客户端速度

首版提供 Top N、自己的成绩与排名、自己附近，以及有上限的游标翻页。公开榜可使用限流的公开读取；自己的成绩查询使用验证后的身份。昵称/头像采用脱敏展示资料，不能当账号标识或开放任意私有资料查询。

新增查询入口采用 `GET /v1/boards/{board}/entries`、`GET /v1/boards/{board}/me` 和 `GET /v1/boards/{board}/around-me`；不改变现有对局 API。响应明确返回榜标识、规则修订、数据版本、分数单位及翻页游标；`me` 的主体由服务端认证确定，不由请求参数挑选。请求大小、页大小和公开查询速率在服务端限量，SDK 不能绕过这些上限。

排序索引与榜范围过滤配套；避免巨大 OFFSET。计算精确名次的范围计数也须纳入基数测试，不能仅凭有索引就承诺常数成本。游标绑定榜及排序位置，响应带数据版本，更新期间允许刷新，不承诺跨多页的全榜快照。

SDK 在结算、模式选择等已知入口预取，以缓存先显示、后台刷新；同榜并发请求合并，写入成功主动使相应缓存过期。自有写入回执包含成绩/更新版本，自己的成绩支持写后立即读取；不能把一条本地成绩直接拼入官方 Top N 并虚构名次。

Steam 数据可见性仍受 Steam 同步影响，采用有截止时间的刷新与成功通知。目标是减少等待和避免必须关窗重开，不承诺外部服务或网络始终零延迟。缓存、并发、超时及重试都有上限，离开页面后取消无用查询。

## 7. 历史清理、忙锁与容量

### 7.1 保留语义

保留期限从已签发对局的过期时间计算，不因新策略缩短旧局。POB 当前常规凭据最长 7 天，裁剪缓冲 3 天；在这些窗口内保持既有批次、nonce、回执和重放结果。首轮不引入“终局满 24 小时就删中间回执”的额外压缩规则。

超过凭据有效期加缓冲后，按现有协议需要保留开局、末批次标记、终局及必要摘要，裁剪中间事件并记完成标志。未结算但已过期的普通局同样可以处理。等待发布、发布结果不明、复核或显式保全的局不按普通终局删除，单独监控保留时长和容量。

摘要/墓碑再按配置保留，初始建议 90 天；到期删除对局及关联审计记录，不删榜成绩、榜定义或人工保全。已过期的客户端队列转成明确终态，停止永久重试。删除后旧凭据仍不得重新登记或补写历史成绩。

### 7.2 分批维护

维护从开局 HTTP 路径移出，提供独立命令供现有 systemd timer 调用，不新增常驻任务平台。增加到期/处理状态索引及最小维护元数据，按游标领取有限候选，重新检查到期时间和保全状态后短事务删除；处理完不再次遍历旧局或全库 JSON。

优先用独立维护表和兼容索引，避免直接给 `runs` 加列破坏现有位置式 `INSERT INTO runs VALUES(...)` 和旧版代码回滚。旧数据按稳定键增量补齐元数据，记录游标，不在启动时整库重建。SQLite 与可选 PostgreSQL 都要验证兼容行为。

初始调优预算：每事务最多删除 128 条事件、目标锁持有低于 50ms；每轮预算 2 秒，批次边界检查后续跑。这些是需要测量的目标，不是对任意机器的保证。维护遇忙锁让路，不强杀事务；超大单局也分批，并在最终保留条件满足后才标记完成。

API 只将 SQLite `SQLITE_BUSY`/`SQLITE_LOCKED` 及对应扩展码映射为可重试 503，覆盖连接、BEGIN、执行和提交边界；确认回滚或提交不明后通过幂等请求恢复。库结构不匹配、数据损坏、磁盘错误和 SQL 缺陷保留独立告警，不能统一伪装为临时网络失败。不要把网络调用放进长数据库事务。

### 7.3 长期容量

容量预算包括每日对局量、每局事件数、平均记录大小、保留窗口、索引、最佳成绩、临时备份和发布切换的峰值。以模拟一年及突发流量验证稳态，不只比较清理前后文件大小；运行时同时观测活跃数据、空闲页、WAL、最老待处理任务和可用磁盘。

常态复用 SQLite 空闲页，不在线盲跑整库 `VACUUM`。修改 `auto_vacuum` 模式涉及数据库准备/重建，不是随手切一个配置即可解决。[SQLite 文档](https://www.sqlite.org/pragma.html#pragma_auto_vacuum)

磁盘警戒默认采用卷容量 20% 与实际备份峰值需求中更保守者，阈值可按实例配置。压力下只清理已到期、归属明确的审计/缓存并减少可选观测，不删除现役账本、待发成绩、人工保全或最后一个可恢复备份。扩容需求提前告警，不到磁盘写满才处理。

策略使用有界模板、实际兼容规则组合和必要榜目录，避免每个显示版本累积一份配置。上线预检计算完整策略及凭证大小；systemd 单服务凭证合计有 1MB 限制，初始在 75% 时告警，超预算在切换前拒绝候选并保留当前服务。必要时把非秘密策略改为权限受控的配置读取，不扩大密钥可见范围。[systemd 文档](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html#Credentials)

## 8. 备份、恢复与可用性

备份工具纳入版本管理，由公共工具处理封装/校验/轮转，项目 layout 说明需要的运行文件和私有配置。运行时发布清单是文件完整性的来源，递归包含公共模块、来源 commit/哈希、依赖清单、项目适配代码、schema 信息和必要启动单元；数据库、策略及签名/发行商密钥一并纳入受限恢复包。

SQLite 使用在线 backup API 取得一致快照，再做完整性检查；不能直接复制热库忽略 WAL。计算哈希及归档使用固定大小缓冲，不把整个数据库 `read_bytes()` 后塞进内存。[SQLite 在线备份说明](https://www.sqlite.org/backup.html)

备份先写 `.partial`，验证数据库、文件清单及哈希后原子封存。封存成功且有可恢复副本后才轮转旧备份、删除该次临时未压缩副本；失败不会删除上一次可用备份。目录扫描不得将临时快照当正式恢复包，也不自动删除人工 operations 保全。

本机保留最近 3 份日备；定期加密/受限传输到已有异机或对象存储并校验，异地日备初始保留 7 份。隔离恢复演练使用独立目录、账本和端口，默认禁止真实外部写榜，验证冷启动、密钥可用、回执重放及适用阶段的成绩查询，不能只运行 `quick_check`。

恢复目标分开验收：每日备份持续成功且副本可读取时，POB 日备的数据恢复点约 24 小时；现有同机备份不能抵御整机磁盘丢失。自有手机榜作为成绩权威前，目标是异地恢复点不超过 5 分钟、恢复用时不超过 60 分钟。两个时间目标以实际演练及异地链路监控为准，尚未满足时明确报告，不声称已有该保护。

手机阶段优先评估成熟的 SQLite 增量异地复制工具，避免频繁全库备份和自写 WAL 协议；例如 Litestream 可持续复制到存储，但具体版本、存储后端、凭证和恢复流程需要验证并固定。已有备份 adapter 保留，故障时不自动引入第二个可写主库。[Litestream 官方说明](https://litestream.io/)

默认仍为单写主服务加异地恢复副本，systemd 自动拉起与客户端重传处理短暂故障；这不等于实时异地高可用。整机故障期间，新开局可能无法登记，永久丢盘也存在恢复点以内的数据损失。若业务要求单机故障期间新局仍能登记，再独立实施共享账本、多接入点和受控故障转移；本 spec 不默认部署三节点集群或新购服务器。

发布先验证候选、容量和恢复包，再优雅切换单写进程；部署流程识别在途外部写榜，保留结果不明状态。回滚切代码与兼容配置，不用旧数据库覆盖切换后玩家的新进度。影响旧读写格式的迁移单独设计并验证，不随日常自动兼容暗中执行。

## 9. 自动化、观测与测试成本

日常自动项由现有构建与服务器运维链路承担：配置导出及兼容校验、模板创榜、周期轮换、分批清理、有限重试、备份轮转、恢复验证、证书续期与异常告警。采用现有运维入口，不额外创建需要人工常驻盯守的后台。

健康检查既验证 HTTP 状态也验证服务标识和可登记状态，区分进程存活、平台依赖异常和实际写入能力。观测按阶段统计登记成功/拒绝、失败原因、写榜延时、发送队列年龄、忙锁、清理积压、磁盘与最后一次异地可恢复时间。网络与平台波动不能计成玩法作弊。

日志用脱敏对局关联标识和错误分类定位，不记录票据、token、签名密钥、原始账号或完整请求正文。告警有去重、恢复确认及边界，不为每次玩家重试单独发一条通知；人工处理入口沿用现有 ZGS 运维链路。

| 执行时机 | 最小覆盖 | 时间控制 |
| --- | --- | --- |
| 公共内核/适配器改动 | 幂等/事务、忙锁、兼容、榜名、保留策略与源码快照合同测试 | 默认快速回归，不启动游戏打通所有模式 |
| SDK/存档集成改动 | 断线补传、取消、终局封存、正常退出续玩、缓存失效 | 聚焦现有 Editor 或隔离 fixture，不能改用户配置 |
| `zgs publish` 常规/complete 门禁 | 复用现有目录、种子与房间合同；complete 选择有代表性的实包流程 | 记录当前耗时与预算，只扩展本次影响的覆盖 |
| 联网实包验收 | 独立测试榜真实登记、结算、写入和读取；常规/续玩/失败恢复代表用例 | 不要求每次每个模式人工通关，不写正式榜 |
| 运维定期验证 | 备份清单、隔离恢复、容量趋势；手机阶段含异地恢复目标 | 与实时请求错峰，失败保留上一可用副本 |

真实玩法通过、测试驱动的快速完成和模拟协议通过分别记录；不能拿快速完成证明玩家正常战斗可通关。已有 Bug 反馈、埋点链路只验证必要关联，不绑定成每次排行榜改动必须重跑全套业务的大测试。

## 10. 分阶段交付及验收

| 阶段 | 最小交付 | 客户端/上线边界 | 必须取得的证据 |
| --- | --- | --- | --- |
| P0 恢复完整性 | 备份工具源码归档、运行清单覆盖公共模块、流式归档、隔离冷恢复 | 仅服务端工具，不要求 POB 发新包；部署另行授权 | 恢复包可独立启动新公共内核；缺模块/缺来源文件会在轮转前失败；大库备份内存有界 |
| P1 服务稳态 | 分批清理、兼容索引/元数据、busy/locked 503、容量/策略预检、RP1 自动模板修复 | 保持现有 API、凭据及规则语义；不迁移玩家榜 | 历史批次仍可重放；过期后可清；锁竞争不撤局；缺 RP1 模板不套用旧规则；旧代码回滚仍可读写 |
| P2 ZE SDK 与 POB 接入 | 提取既有客户端流程、统一榜标识、接入版本配置自动导出；核对已有重签修复 | SDK/选榜改动需要新包，先测试分支验证，正式发布由用户决定 | 常规、无尽续玩、代表周常/爬塔路径；结算立即刷新；重启不复活终局；包内无服务端秘密 |
| P3 手机及自有榜 | 原子自有成绩表、查询/缓存、一个真实渠道认证、异地增量保护 | 独立测试环境接入，不切换现有 POB Steam 权威榜 | 真实手机账号端到端；提交响应丢失后无重复；精确名次与翻页在预计规模内达标；恢复点/恢复时间实测达标 |

每阶段先执行最便宜的充分检查，再对未覆盖风险补测。阶段验收不能只用单元测试数量表示；需要相应真实存储、包体或恢复证据，完成一阶段不代表其他阶段已经实现。

## 11. 最终验收清单

1. 普通升级版本、配置中的合法房间增删/路线变化、周常切换和同规则新赛季，通过可信构建导出即可生效，不手改线上榜清单；不兼容改动明确中止自动切换并保留当前服务。
2. 正常新局、暂停、断网、退出重进、重复回调及终局重启不丢幂等关系；未取得凭据与明确校验失败分开提示；网络和存储忙锁不永久误拦正常局。
3. 在有效期内的旧客户端请求/批次得到兼容结果；到期清理不会破坏自有最佳成绩、人工保全或已承诺的恢复窗口；维护不长期持有全局写锁。
4. 对预计一年的数据、突发流量和大库备份验证时间/内存/空间预算；数据库空闲页、清理积压及异地恢复滞后均可观测，不能仅凭进程活着判定稳定。
5. Steam 与自有榜各自使用正确的权威数据；自有提交原子幂等，查询排序一致、写后可见；不同项目及测试/正式环境不串身份、不串榜。
6. 完整恢复包含公共代码及来源、依赖、数据库、配置与必要密钥；替换主机后能恢复读写。演练不触碰正式 Steam 榜，也不覆盖现役数据库。

## 12. 保留的人工决策

首个手机渠道及其账号绑定需求，在 P3 接入前确定；不为尚未选择的所有商店提前开发适配器。精确服务指标按预计玩家规模测定，达不到预算时再扩容或切 PostgreSQL。

破坏性计分变更、密钥撤销/轮换、账号归属争议、平台接口政策变动、灾难接管及扩容仍需要明确决策。日常版本号、关卡配置和轮换不应再次变成逐次运维任务；“免维护”不以弱化验证、删除唯一恢复副本或隐瞒服务不可用为代价。
