# 玩家反馈的提交结果与排查依据

日期：2026-11-02。状态：已授权开始实施，尚未发布。前一版本地候选仅屏蔽可重试错误的失败提示，不能视为本方案已经落地。

## 目标和范围

玩家能知道内容有没有保存、服务器有没有确认收到、是否需要自己操作；维护人员能按同一个反馈编号还原结果，不把一次网络错误当成整条反馈失败，也不因为补传产生重复业务通知。

覆盖 ZE Feedback、同仓 Analytics SDK、Analytics 接收服务和现有反馈查询页，以及 POB 的提示/面板绑定。复用现有队列、反馈面板和查询页，不另建工单中心，不承诺反馈已被人工阅读或游戏问题已被修复。本次实施覆盖源码、测试和本地联调；服务部署、包发布和正式 POB 依赖采用仍遵守各自授权边界。

## 核对到的现状

- POB 的 `POBFeedbackIntegration` 配置为不显示提交中、显示成功和带错误码的失败；`BugReportPanel` 在本地打包入队后关闭，按钮锁仅覆盖本地提交过程。
- 基线 `68cb1f8b3adc2eb92141b02ed9949267c7f4e103` 的 Analytics SDK 已持久保存提交编号和幂等键；重试复用原 ZIP 和编号。后台退避为 60/300/900/1800 秒，部分不可短期重试错误进入 6 小时冷却。因此 `Retryable=false` 也不等于这条反馈永久终止。
- 当前状态通知把单次上传失败直接交给 UI；客户端还将“服务器成功、但本地队列清理持久化失败”作为失败通知。仅过滤 `Retryable` 不能解决这些情况。
- 本地队列最多 10 条，新增时会淘汰旧条目；7 天过期清理在初始化执行。目前缺少供玩家重开面板查看的逐条提交结果。

## 状态与玩家看到的内容

“上传尝试结果”“整条反馈的送达状态”“通知/后续处理状态”分别记录。失败次数、重试耗尽或等待时间均不能单独证明服务器没有收到。

用户确定的状态弹窗仅有以下四条，标点按原文保留：

1. **提交中…**
2. **自动重试中…**
3. **提交成功，感谢反馈。**
4. **提交失败（Fxxx）**

具体原因、附件问题、处理方法和停止补传说明只在详情显示，不增加状态弹窗。只有仍安排自动补传/确认时才显示“自动重试中…”。输入校验就地显示，不另弹一套提交状态提示。

| 情况 | 玩家提示与操作 | 结果判定 |
| --- | --- | --- |
| 点击提交，正在准备本地包 | 按钮显示“提交中…”，同一份内容不可连点；输入保留 | 尚未确认本地可靠保存 |
| 包和队列已持久保存，开始上传 | “提交中…”；允许关闭面板 | 本地已保存，不是提交成功 |
| 首次网络异常，仍安排自动重试 | “自动重试中…”；详情说明已保存、无需重复提交 | 继续原请求/后台确认，不另起并行上传 |
| 收到匹配提交编号和内容的有效成功回执 | “提交成功，感谢反馈。” | 只代表服务器已可靠接收 |
| 服务器确认接收正文，但部分附件未接收 | 同一成功提示，附件问题放详情 | 保留接收成功，不引导重传整份 |
| 打包/保存等在任何网络发送前就失败，或能证明本条未接收的明确拒绝 | “提交失败（Fxxx）”；详情给出原因和处理方法 | 此时才使用失败语义 |
| 证书、认证、文件等错误阻止继续，但此前可能已送达 | 仍安排复查时用“自动重试中…”；否则仅详情说明需处理 | 不能把它当成未送达证明 |
| 达到本地保留期限，仍无可靠结论 | 停止重试提示；仅详情说明已停止、结果尚未确认 | 不伪造失败，也不再显示“自动重试中…” |

沿用入队后立即后台上传的异步入口，不额外增加 10 秒前台等待。原请求仍在上传时不伪称已经重试，也不把超时当成失败倒计时。游戏关闭时不承诺持续联网补传；下次启动且联网、配置可用时恢复。恢复条目只有在配置可用且仍安排补传时才提示自动重试。

## 最小交互

- 在现有反馈面板增加简短的“最近提交”区域：显示尚待确认的条目及最近结果、提交时间、反馈编号和下一步。待处理条目最多沿用现有 10 条限制；最近已结束结果单独最多保留 10 条最小记录，不保存完整历史反馈中心。
- 同一草稿首次提交后绑定一个稳定编号。重开面板、点“立即重试”、自动补传、进程重启都操作原条目；立即重试先确认回执，并服从单条正在执行的请求与退避限制。玩家明确“提交另一条反馈”才创建新草稿和编号，不按相同文字误合并两条独立反馈。
- 本地未能保存时保留输入和附件选择，不关闭表单；已经可靠入队则可关闭表单，重新打开仍能看见状态。跨启动只保证已经可靠保存的内容，不把内存中的失败草稿说成已持久保存。
- 同一条反馈的短提示使用同一个提示分组更新；每次重试不弹新提示，成功只提醒一次。恢复多个旧队列条目时只显示一次“自动重试中…”；逐条结果在面板查询，不在启动时刷屏。提示去重状态随最小结果记录保存。
- 失败弹窗保留错误码，短原因、可执行动作、日志和请求编号放在详情。成功文本与上传进度不表达人工处理进展。

## 客户端与服务端的确认合同

1. **一条反馈一个身份。** 在首次打包时确定随机提交编号，原 ZIP 内容在后续重试中保持不变。服务端以经校验的产品身份和提交编号为业务键，并绑定原始请求内容摘要；同键同内容返回同一逻辑接收记录，同键不同内容拒绝覆盖且不自动换编号。部分接收时另记保存后包的摘要，不能用改写后的摘要破坏原请求重试去重。
2. **回执是成功依据。** 保留 `/upload` 对旧客户端的兼容字段，新增明确的协议版本、提交编号、接收结果和可核对的回执信息；文件和接收记录可靠落地后才返回成功。新客户端校验响应结构与身份，不能仅凭 HTTP 2xx 或中间页判成功。
3. **先查后重传。** 新增最小的、受现有上传认证及产品/编号/内容证明约束的接收结果查询，只返回必要接收信息，不暴露正文、联系方式、附件下载地址或其他反馈。具体路径在 Analytics 所属 API 路由登记中确定。回执查询不存在、查询超时或某个 edge 暂无记录，都只代表未确认；有可靠成功回执则立即收敛为成功。
4. **跨 edge 按业务身份收敛。** 腾讯与 Worker 的持久接收记录、复制和权威汇聚使用同一业务键；下游通知也使用该键去重。网络隔离期间可分别保有物理副本，不宣称全局瞬时只有一个文件；最终不得重复创建业务通知/记录。同键内容冲突必须可诊断且禁止覆盖。幂等/回执保留覆盖全部允许的重试窗口，本次不新增会提前删除这些依据的清理策略。
5. **已接收后不退回失败。** 一旦服务器确认收到，本地队列标记/删除失败只作为本地清理告警，保留原编号重试清理或幂等确认；玩家仍看到成功。通知投递或内部流转失败也不改变接收成功。
6. **错误不直接决定整条状态。** 现有 `FeedbackUploadFailure` 和短码保留为单次尝试诊断；增加独立的可持久查询的提交状态。403/413/TLS 等首先决定当前尝试和下一步；存在先前未知尝试时，不能据后一次拒绝宣称过去从未接收。仅在有足够依据时显示最终失败。

## 本地可靠性和生命周期

- 复用原持久队列，增加最小状态记录与只读快照接口；保存提交编号、内容摘要、尝试状态、已确认接收标记、最近错误、下次重试时间和通知标记。继续对存储写失败做显式处理，不凭内存状态假称可靠保存。
- 重开反馈页、Fast Play 和进程重启后恢复状态；静态重置仅清理订阅/运行时对象，不丢失持久身份。旧队列读取兼容，不重写已有幂等键；缺字段的旧条目采用兼容迁移，不编造历史成功或失败。
- 队列满时拒绝新入队并保留新表单，告诉玩家已有内容等待上传；不再为接收新反馈静默淘汰旧反馈。最近已成功条目的最小记录可按上限清理。
- 沿用 7 天待上传包保留边界，使用明确到期时间；运行期间及启动时都检查，且不与在途上传竞争删除。清理前记录“已停止重试/结果未确认”，不得删除仍在上传或恢复中的文件。没有成功回执的状态不因清理自动变成失败。
- “服务器已确认”优先于较晚到达的失败回调；重复回调不得重复通知或重新打开失败状态。改动按原存档/平台隔离规则验证，不写玩家正常配置。

## 我们如何看清结果

- 现有 Analytics 反馈详情按提交编号串起结构化反馈事件、接收回执、文件与通知结果。分别显示“服务端已收到”“客户端最后上报的状态”“通知待投递/已投递”，并注明观测时间与来源；客户端失联时不能把旧状态当当前状态。
- 每次尝试保留提交编号、阶段、时间、次数、HTTP/短码、脱敏请求编号、下一次动作。状态变更另记一次，最终接收成功覆盖该条的“送达未确认”汇总；不抹去之前的超时排障记录，也不把每次重试计作新反馈或最终失败。
- 本机未联网且从未上报的内容，服务端无法知道；面板和本地日志提供依据，恢复联网后补报必要状态。查询页没有记录时显示“尚无接收依据”，不写“玩家没有提交”。
- 可重试错误做尝试级统计和持续积压/老化观测；最终未送达、内容损坏、身份冲突、持续无法补传分别记录。沿用现有运维告警接收配置，不把一次网络波动转成一条业务失败通知，不另增未经授权的收件人。
- 不在日志/状态查询返回上传密钥、完整错误原文、签名下载地址或玩家本机完整路径；正文和联系方式继续走原受控反馈内容渠道。

## 实施顺序与边界

1. 先核对 Analytics 实际部署版本和在办修改，落实上面的状态、回执和去重测试样例；本地现有过滤改动只作为补丁候选保留，不单独当作整套优化发布。
2. 在 Analytics 服务源码补充兼容的接收身份、结果查询和跨 edge/通知去重，以及现有查询页按编号的关联。旧客户端仍可上传；无稳定身份的历史客户端不承诺可自动去重或反向补齐历史结果。服务变更、增量存储迁移和部署按原服务所有者路线进行。
3. 在 ZE 同仓 Analytics SDK 实现状态持久化、确认与重试收敛、队列上限/到期反馈、接收成功与本地清理解耦；在 Feedback 包实现状态展示与只读查询接口。旧 API 和枚举序列化保持兼容，新增枚举只追加，事件仍保留单次尝试语义。受影响包版本、依赖与说明同步更新。
4. 在 POB 现有反馈面板和提示适配中启用新体验，补齐现有 13 语；通用上传状态留在上游包，POB 只保留界面和项目数据绑定。此功能只涉及本地提交与后台网络请求，不复制给其他玩家，不改变共享世界或联机权威。
5. 先验证服务端和包，再通过 POB 的原 Editor 队列验证实际面板流程。发布顺序为兼容服务端在前、SDK/Feedback 发布在后、POB pin 已验证的兼容提交最后；上线前核对两 edge 均支持该协议。所有提交、推送、迁移和生产部署仍需对应明确授权，本方案不替代该授权。

回滚客户端时保留原编号、ZIP 和已确认依据；服务端保留兼容 API 与已写接收/去重记录，不靠删库或重置队列回滚。未具备协议能力的服务端不能承接新确认流程；发布门应阻止这种版本组合，客户端也不得靠无限盲目重传掩盖不兼容。

## 必须证明的结果

使用合成反馈、隔离存储与 staging 接收端，不改生产配置、不向正式业务收件人发送测试反馈。

| 场景 | 可观察结果 |
| --- | --- |
| 正常提交、连点、重开面板 | 一个草稿只有一个编号；成功一次；关闭/重开后状态可查 |
| 请求尚未送到就断网，恢复联网 | 本机可靠保存且显示待确认；恢复后原编号补传成功 |
| 服务端已落地但回执丢失，重试落到另一个 edge | 不弹最终失败；确认后成功；一个逻辑接收记录和一次业务通知 |
| 查询未命中、edge 隔离、复制延迟 | 保持未确认，不把未命中当失败；取得可靠回执后收敛 |
| 超时/5xx 后明确拒绝；TLS/认证错误且存在旧的未知尝试 | 当前原因和下一步可见；诊断事件与整条状态分开，不错误断言历史未接收 |
| 成功后本地清理写失败；通知投递失败 | 玩家仍成功；维护页/日志指出具体后续故障，不重复业务反馈 |
| 正文接收、部分附件被过滤；成功后迟到失败回调 | 显示接收成功及附件说明；成功不退回失败 |
| 队列满、包损坏、到期、游戏跨启动恢复 | 不静默淘汰；动作/原因明确；不伪造送达结论、不换编号；到期不删在用文件 |
| 旧队列和旧客户端；同编号不同内容 | 兼容读取/上传；冲突拒绝覆盖且可排查，不隐式生成第二份 |
| POB 实际面板、各语言文本、离开反馈页继续游戏 | 按钮和提示无歧义，状态可再查看，无正常存档/配置写入；本地提交不影响其他联机玩家 |

包级状态测试和服务端测试不能代替 POB 实际 UI 检查，也不能代替跨 edge staging 验证。发布后仍需核对实际版本与最小接收/去重结果，不能用“包已升级”代替行为证据。
